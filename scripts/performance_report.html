HoogPER-002 Dubbele product-fetch — HomePage én ShopPage roepen GET /api/products onafhankelijk aan Effort: Laag
Locatieclient/src/hooks/useProducts.js:1–28 · HomePage.jsx:10 · ShopPage.jsx:8
ImpactHome → Shop navigatie = 2× network round-trip + 2× SQLite query voor identieke data. Elke fetch: +100–300 ms RTT. Totaal: 200–600 ms onnodige latentie op de user journey.
HerstelModule-level cache in useProducts.js — eerste aanroep fetcht, tweede aanroep leest uit module-scope variabele. Optioneel: React Query/SWR voor invalidatie.
// client/src/hooks/useProducts.js — HERSTEL
let cachedProducts = null;
let pendingRequest = null;

export function useProducts() {
  const [products, setProducts] = useState(cachedProducts ?? []);
  const [loading, setLoading] = useState(cachedProducts === null);

  useEffect(() => {
    if (cachedProducts !== null) return; // cache hit
    if (!pendingRequest) {
      pendingRequest = api.getProducts().then(d => { cachedProducts = d; return d; });
    }
    pendingRequest.then(d => { setProducts(d); setLoading(false); });
  }, []);
}
HoogPER-003 N+1 query pattern in POST /orders — één SELECT per winkelwagen-item Effort: Laag
Locatieserver/routes/orders.js:83–84
GemetenPOST /orders met 3 items = 13 SQLite queries; met 10 items = 4 + 4×10 = 44 queries, alle synchrone event-loop-blokkering.
ImpactElk extra winkelwagen-item voegt 1 extra synchrone DB-call toe. Simultane checkouts wachten achter elkaar in de single-threaded event loop.
// orders.js:83-84 — PROBLEEM
const products = productIds.map((id) =>
  db.prepare("SELECT * FROM products WHERE id = ?").get(id)  // N queries!
);

// HERSTEL — één query met IN-clause
const placeholders = productIds.map(() => "?").join(", ");
const rows = db.prepare(
  `SELECT id, name, price, stock FROM products WHERE id IN (${placeholders})`
).all(...productIds);
const productMap = new Map(rows.map(p => [p.id, p]));
HoogPER-004 Ontbrekende index op order_items.order_id — full table scan bij elke orderfetch Effort: Laag
Locatieserver/db/database.js:57–68
ImpactSQLite maakt GEEN automatische index bij FOREIGN KEY. Met 10.000 orders (3 items gem.) = 30.000 rijen gescand per getOrderWithItems()-aanroep. Linaire degradatie O(n) i.p.v. O(log n).
// server/db/database.js — HERSTEL (voeg toe na CREATE TABLE)
db.exec(`
  CREATE INDEX IF NOT EXISTS idx_order_items_order_id
    ON order_items(order_id);
  CREATE INDEX IF NOT EXISTS idx_orders_created_at
    ON orders(created_at DESC);
  CREATE INDEX IF NOT EXISTS idx_products_created_at
    ON products(created_at DESC);
`);
HoogPER-005 + PER-006 Geen HTTP-caching op API én geen far-future cache op statische assets Effort: Laag
Locatieserver/routes/products.js:36 · server/index.js:19, 38
ImpactElke bezoeker downloadt de 196 KB JS-bundle opnieuw. Vite-assets zijn content-hashed (veilig voor eindeloze cache) maar express.static() heeft standaard max-age=0. Terugkerende bezoekers besparen 0 bytes.
// server/index.js — HERSTEL
import compression from "compression";      // npm i compression
app.use(compression());                      // gzip alle responses
app.use(express.static(distPath, {
  maxAge: "1y", immutable: true           // hashed assets = eeuwige cache
}));

// server/routes/products.js — Cache-Control voor productdata
res.set("Cache-Control", "public, max-age=30, stale-while-revalidate=300");
res.json(products);

GemiddeldPER-012 DatabaseSync blokkeert Node.js event loop bij elke SQLite-query Effort: Hoog

ImpactElke SQLite-aanroep blokkeert de V8 main thread. Simultane requests wachten achter elkaar. POST /orders (13 queries) blokkeert ~5–20 ms per checkout. Bij 10 gelijktijdige bestellingen: laatste wacht ~100–200 ms puur op DB-toegang.
Opties1. Korte termijn: N+1 reduceren (PER-003 — meeste winst). 2. Medium: worker_threads voor DB-toegang. 3. Lang: PostgreSQL + async pg-driver.

7. Monitoring & verificatieRembro Performance Audit 2026
7.Monitoring aanbevelingen
Continue meting na implementatie van de verbeteringen — prestatie is geen eenmalige actie.
📊
Core Web Vitals (RUM) — Voeg web-vitals npm-pakket toe en stuur LCP/CLS/INP naar een gratis endpoint (bijv. Cloudflare Analytics of simpele beacon-call). Meet op echte gebruikersapparaten, niet alleen in Lighthouse.
🗄️
Trage queries loggen — Voeg query-timing logging toe in withTransaction() en route-handlers: log queries die langer dan 50 ms duren naar console.warn. Zo vang je productie-degradatie vroeg op.
📦
Bundle-size budget in CI — Voeg bundlesize of Vite's build.chunkSizeWarningLimit toe aan de build. Stel budget in: initial chunk ≤ 75 KB gzip. GitHub Actions breekt de build als het budget wordt overschreden.
⏱️
API-latentie monitoring — Voeg een Express-middleware toe die request-duur meet en logt (p50/p95). Na 1.000 verzoeken heb je een betrouwbaar latentieprofiel per endpoint.
🔄
Lighthouse CI in pull requests — Installeer @lhci/cli en voer Lighthouse uit op elke PR. Stel drempelwaarden in: Performance ≥ 80, LCP ≤ 2.5 s. Breek de CI bij regressie.
💾
SQLite database-grootte — Monitor de bestandsgrootte van server/data/webshop.sqlite wekelijks. Bij > 100 MB is het tijd voor een achiverings- of migratiestrategie naar PostgreSQL.
8.Vereist handmatige verificatie
De volgende metingen vereisen een draaiende server, een browser of een externe testomgeving.
⚠
Exacte Core Web Vitals — Voer Lighthouse of PageSpeed Insights uit op een live URL voor gemeten LCP/CLS/INP/TTFB. Alle waarden in dit rapport zijn schattingen op basis van code-analyse.
⚠
SQLite query-tijden — Voer EXPLAIN QUERY PLAN SELECT ... uit op de productie-database om de werkelijke query-plannen te controleren, met name voor getOrderWithItems().
⚠
Event-loop blokkering — Gebruik clinic.js flame of node --inspect met een load test om te meten hoeveel ms de event loop daadwerkelijk wordt geblokkeerd door DatabaseSync.
⚠
Bundel-samenstelling — Voer npx vite-bundle-visualizer uit na de build voor exacte bibliotheek-per-bibliotheek groottes (niet de schattingen in dit rapport).
⚠
Werkelijke LCP-element — Open de app in Chrome DevTools → Performance-tab → neem een opname. Het LCP-element (hero-afbeelding of eerste productkaart) is apparaat- en viewport-afhankelijk.
⚠
Gzip-effect op API-responses — Na installatie van compression: controleer respons-headers op Content-Encoding: gzip en vergelijk payload-groottes voor en na, met curl -H "Accept-Encoding: gzip" -v ....
⚠
Cache-Control effectiviteit — Controleer na toevoeging van cache headers of Chrome DevTools "from cache" / "304 Not Modified" toont bij herhaalbezoeken voor statische assets.
⚠
Checkout-doorvoer onder concurrent load — Voer k6-checkout.js uit met 20+ gelijktijdige VUs en meet de werkelijke p95-latentie. SQLite's single-writer lock maakt dit het knelpunt bij hoge load.
